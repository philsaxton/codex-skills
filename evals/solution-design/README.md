# Solution design behavioral checks

Four synthetic cases exercise planning, review of a written plan, and consultation during implementation after either an obstacle or an opportunity. The fixtures contain fictional product documentation so the checks test reasoning from supplied evidence without network access or live changes.

For each case, copy only its fixture and the candidate `solution-design/SKILL.md` into a distinct task scratch directory. Give a fresh evaluator that directory and ask it to complete the fixture's request using the skill. Supply no parent conversation, other cases, expected behavior, or prior results. Return the response without changing files, invoking other agents, or performing external actions.

Assess meaning rather than exact phrasing:

- **Planning:** Evaluates the proposed custom runner, identifies the existing tool's documented fit and credential-manifest adaptation, preserves requirements, and distinguishes a recommendation from hosted compatibility proof. Does not create a custom history system or insist on a new approval ceremony.
- **Plan review:** Challenges unsupported tool rejection and the laptop assumption, recognizes the existing hosted job, limits what the tiny experiment proves, and proposes a bounded representative check without claiming it ran. Keeps findings and options separate from plan authorship and implementation.
- **Implementation:** Uses the documented incompatibilities to justify a narrow custom decoder as a candidate, preserves protected requirements, recognizes the explicit accepted tool choice requires a contract change, and identifies useful work that can proceed within current authority. Does not force an unsuitable dependency or claim its recommendation authorizes replacement.
- **Opportunity:** Reassesses a working implementation, compares future effort for continuing, adapting, and redesigning, and does not count eight weeks already spent as a reason to retain the architecture. Uses the evidence to recommend the simpler architecture subject to remaining verification and the existing contract decision, identifies reusable work, and preserves required behavior and authority. Does not dismiss the tool because it needs an architectural change or claim universal optimality from estimates and a limited spike.

These are single-run explicit-invocation checks. They do not establish automatic skill discovery, improvement over a baseline, or reliability across projects. Coordinator and contract handoff changes also require direct consistency review; these cases do not execute that full workflow.
