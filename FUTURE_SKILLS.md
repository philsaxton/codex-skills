# Future Skills Candidate Backlog

This document records workflow patterns that may deserve reusable Codex skills and proposed evaluations of them. Recording a plan here does not authorize implementation, activation, or changes to project policy. Project instructions and user direction remain controlling.

## Qualification criteria

Promote a pattern only when:

- evidence from multiple projects, or repeated failures in materially different workflows, shows a stable need;
- it contains a non-obvious invariant or decision process that improves outcomes beyond ordinary model capability;
- its trigger boundary is narrow enough to avoid burdening routine work;
- the portable behavior can be separated cleanly from project terminology, schemas, paths, permissions, and authority rules;
- it owns a coherent outcome without duplicating an existing skill; and
- realistic examples exist for forward-testing the smallest useful skill.

## Standalone-role principle

Every reusable role skill must be operationally standalone. It may require task evidence or authoritative inputs, but it must not assume that another named skill ran or exists. References to other skills describe optional overlap or artifact ownership, never runtime prerequisites.

When a formal controlling artifact is absent, use the best available evidence, such as the user request, issue, accepted plan, relevant documentation, and current deliverable. Publish any inferred intent, scope, criteria, or assumptions in the output together with their evidence and material uncertainty; inference remains provisional and must not silently become approved authority. Withhold only a judgment that genuinely requires authority the available evidence cannot establish.

### Workspace temporary files and worktree placement

- **Problem and intended outcome:** The user reports repeated permission interruptions and scattered temporary files/worktrees. Establish predictable garage-local locations so agents can use permitted workspace storage and cleanup can be bounded. Proposed defaults are `tmp/<task-id>/` for disposable task files and `.worktrees/<app>/<task-id>/` for application worktrees; retain existing local spelling/conventions, including `.worktree/`, when appropriate. These paths are workspace policy, not mandatory application layout.
- **Setup and use:** Extend workspace setup to record the chosen locations and ignore boundaries in local governance. Direct explicit temporary-file creation there and configure process-scoped temporary-directory settings for tools that honor them; do not assume every tool honors an environment variable. Keep reports, recovery evidence, deliverables, and active task files distinct from disposable scratch. Check the current host's effective writable roots: `/tmp` or `/private/tmp` may already be allowed, and workspace containment alone does not override protected paths.
- **Bounded scratch cleanup:** A deterministic helper should preview and remove only explicitly selected, completed task scratch directories under a trusted, designated root. It must reject arbitrary roots, traversal, symlink escapes and unsafe path changes during deletion, and refuse the workspace root, application repositories, worktrees and retained evidence. Do not infer disposability solely from age or a directory name, or erase another active agent's scratch space. A standing command approval must not become a broad `rm` capability; if execution needs greater permissions, the helper and its executable inputs must be protected from agent modification. In-sandbox execution remains subject to the sandbox.
- **Worktree lifecycle:** Create worktrees from the owning application repository into its selected garage location, with collision checks. Use Git-aware lifecycle operations rather than the scratch remover. Worktree directories and their shared Git metadata both need effective access; garage-local placement can reduce location-related interruptions but cannot promise approval-free Git operations or control an app-managed worktree location that the host does not expose.
- **Ownership and overlap:** Proposed split: `workspace-setup` establishes directories and local instructions; a small scratch helper handles the distinct disposable-file operation; [cleaning-git-repositories](cleaning-git-repositories/SKILL.md) retains merged/clean/inactive worktree checks and deletion decisions. Workspace trust review remains relevant only for the specific greater-permission executable-input concern. Recurring scratch use is now separated into `workspace-scratch` below; do not duplicate the existing Git cleanup role.
- **Validation needed:** Exercise actual temporary-file routing and tool settings, concurrent tasks, retained migration evidence, traversal/symlink substitution, occupied paths, multiple app worktree namespaces, dirty/active worktree refusal, and protected shared Git metadata. Test that an approved helper invocation cannot be redirected outside its assigned scratch scope.
- **Initial implementation:** Implemented at the user's request as an extension of [workspace-setup](workspace-setup/SKILL.md), not a separate skill (2026-09-04). The new scaffold establishes ignored scratch/worktree locations, local operating instructions and a named-task scratch helper with explicit completion, preview and apply. Existing garages use additive setup; no live workspace was changed. Nineteen executable tests and an independent bounded review cover the new helper and existing scaffold; [validation](docs/evidence/2026-09-04-workspace-local-storage-validation.md) records scope and concurrency limits. No permission rule was added; Git-aware worktree deletion remains with the existing cleanup workflow.

### Workspace trust review

- **Trigger boundary:** Review whether agent-editable scripts, imports/dependencies, symlink targets, or configuration can change tooling trusted to execute with greater permissions, especially under standing outside-sandbox command approval. Do not trigger a broad vulnerability audit or review every ordinary sandboxed command.
- **Reusable invariant/workflow:** Identify the trusted invocation and its actual execution permissions, trace the relevant executable inputs and who can change them, and distinguish observed facts from assumptions. Ordinary sandbox execution remains sandboxed; skills do not bypass it. Approval of a command does not bind the contents of the script or dependencies that command later executes. Report the concrete mismatch and proportionate remediation without silently changing trust or approval policy.
- **Must remain project-specific:** Approved commands, installation/dependency mechanisms, writable and protected paths, intended trust owners, permissions, and authority to change approvals or tooling.
- **Dependencies and overlap:** Standalone review, with no prerequisite skill. Workspace refactoring keeps only a focused check when a migration changes what trusted tooling executes or who can edit it; that check must not depend on this future candidate.
- **Evidence needed before authoring:** Cases across distinct workspaces showing mutable executable inputs crossing an intended permission boundary, alongside ordinary sandbox cases that must not be flagged. Establish which decisions add value beyond existing permissions and routine review.
- **Current disposition:** Future standalone candidate, recorded at the user's request (2026-09-04). Not implemented. Replaces the earlier broad trust-hygiene idea with this narrower execution-trust review.

### Governed change control and evidence provenance

- **Trigger boundary:** Changes whose governing policy requires state transitions or consequential completion actions to be bound to exact artifacts, approvals, and durable evidence. It should not trigger for ordinary edits, routine verification, or informal progress tracking.
- **Reusable invariant/workflow:** Preserve a verifiable chain from authorized starting state to applied result. A candidate could bundle tracking-first state transitions, exact artifact identity, approval binding, risk-proportionate checkpoints, atomic completion application, and post-application fidelity checking. The reusable contract is that approval and completion apply to the same identified payload, and that the resulting state can be mechanically reconciled with it.
- **Must remain project-specific:** Status vocabulary and allowed transitions; evidence locations and retention rules; record schemas; designated authorities; protected files; required hashes or identifiers; retry limits; and which actions require checkpoints or atomic application.
- **Dependencies and overlap:** Complements the thin `coordinator` skill's routing and evidence-aware handoffs. Git worktree, commit, merge, and push mechanics belong to existing dedicated Git/worktree workflows unless repeated evidence demonstrates a gap that those skills cannot own.
- **Evidence needed before authoring:** At least two distinct control planes with the same provenance invariant but different records and terminology; examples where ordinary coordination loses artifact/approval identity; and pressure tests showing which checks must be mandatory versus project-configurable.
- **Current disposition:** Evidence-tested hold (2026-08-26; tasks `01a03c7a-1e89-72e3-977f-014c1c6fcf06` and `01a03c84-2dd2-71a1-aa43-20dac6e816e8`). Distinct BLG-VTT software-qualification and VendingOps reviewed-purchasing control planes demonstrate real artifact/approval identity failures and a shared provenance invariant, while also proving that hashes and batch atomicity are configurable rather than universal. However, six fresh no-skill baselines correctly rejected stale or ambiguous authority, preserved adverse evidence, reconciled successful application, and avoided ceremony for ordinary edits and routine verification. The current `coordinator` already covers the same portable core, and no concrete handoff gap appeared. Do not author until a fresh failure demonstrates a distinct, non-duplicative discipline beyond coordinator and ordinary verification behavior.

### Governed review loop

- **Trigger boundary:** Workflows that genuinely require separated authorship, independent requirements review, implementation, and final verification because independence is mandated or materially reduces authority, safety, irreversibility, or broad-impact risk. It should not turn normal implementation or ordinary code review into a four-role ceremony.
- **Reusable invariant/workflow:** Keep role ownership and judgments independent; bind implementation to approved requirements; route findings to the role that owns the underlying artifact; preserve adverse findings through focused remediation; and allow completion only after final verification of the current implementation against the approved requirements.
- **Must remain project-specific:** Role names, freshness rules, review report formats, retry counts, acceptance gates, escalation authorities, allowed-file boundaries, required evidence, and the exact meaning of approval or completion.
- **Dependencies and overlap:** Specializes the staged path already recognized by `coordinator`; it must not absorb general delegation, workspace orchestration, or specialist implementation. Workspace isolation may use existing Git/worktree skills, but Git operations are not the review loop itself.
- **Evidence needed before authoring:** Repeated use in more than one project; examples where a general coordinator handoff is insufficient; demonstrated independence failures or gate confusion; and forward tests proving a dedicated skill selects the governed loop only when warranted.
- **Current disposition:** Evidence-rejected as a standalone skill (2026-08-26; fresh task `01a03c83-02a5-7181-8200-5f5372310aa2`). Completed governed workflows recur across client-agent-workspace, acks-app-ocaml, and affuture-social, including real independence violations, gate confusion, adverse remediation loops, and unbounded review. That evidence validates the problem but not a distinct portable skill: the shared invariants are already owned by `coordinator`, `contract-author`, `contract-reviewer`, ordinary review, and verification guidance, while the differing role topology, freshness rules, gates, retries, reports, and evidence locations are project policy. Do not author unless a future failure demonstrates a non-duplicative narrow boundary that the current coordinator cannot handle.

### Contract reviewer

- **Trigger boundary:** A proposed contract, specification, or other recorded task basis needs a separate review of whether another practitioner could implement and verify it without inventing requirements. It should not trigger for drafting, collaborative redlining, or review of a completed implementation.
- **Reusable invariant/workflow:** Evaluate intended outcome, scope and non-goals, internal consistency, feasibility, acceptance criteria, and material risk coverage; return prioritized findings, questions, and a clear readiness conclusion without silently rewriting the contract. If no formal contract exists, state the inferred review basis, requirements, evidence, and uncertainty without treating them as approved authority.
- **Must remain project-specific:** Approval authority, required sign-offs, severity labels, domain checklists, templates, record formats and locations, versioning conventions, deadlines, and escalation rules.
- **Dependencies and overlap:** `contract-author` may own a formal contract and `coordinator` may own assignment or routing when those skills are present; neither is a runtime prerequisite. A contract-reviewer skill would own only the review judgment and remain distinct from later review of the delivered result.
- **Evidence needed before authoring:** Develop independent cross-project scenarios showing recurring specification-review failures, useful reviewer decisions, and a stable boundary from editing and final review. Only afterward should project role documents be used as comparison material, not as design evidence.

### Final reviewer

- **Trigger boundary:** A completed deliverable needs an outcome-focused review against agreed requirements before it is represented as complete. It should not trigger for proposal or contract review, implementation work, remediation, or routine checks performed during development.
- **Reusable invariant/workflow:** Inspect the current deliverable and requirements, reproduce or examine proportionate verification, trace observable outcomes to acceptance criteria, assess material gaps and residual risks, and issue a clear conclusion. If no formal contract exists, enter a clearly labeled inferred-intent or general-review mode: publish the inferred intent and review basis in the report, invite human correction, report defects and risks normally, distinguish the result from verified conformance to an approved contract, and withhold only a formal acceptance or completion judgment that truly requires confirmed authority. The reviewer reports findings rather than editing the work under review.
- **Must remain project-specific:** Release gates, approval authority, environments, tools and commands, report templates, evidence storage, artifact identifiers, sign-off rules, and remediation or escalation policy.
- **Dependencies and overlap:** `coordinator` may provide routing or separation and `contract-author` may provide formal criteria when those skills are present; neither is a runtime prerequisite. Contract review judges whether the specification is ready, while final review judges the delivered result against the best supported review basis.
- **Evidence needed before authoring:** Develop independent cross-project examples where a distinct final review changes outcomes beyond ordinary testing or peer review, plus boundary tests separating it from contract review and implementation. Compare project role documents only later, after the portable concept stands on independent evidence.
- **Current disposition:** Evidence-tested hold (2026-08-25; fresh task `01a03c1c-cbfb-7531-a2d4-71b5af10ffe7`). Formal-contract controls across completed software, automation, and operational-document deliverables already inspected current artifacts, challenged passing checks, traced outcomes to criteria, reported residual risk, avoided editing, and issued appropriately scoped rejection decisions without a target skill. Two materially different no-contract controls did omit a clear inferred-intent/general-review label, an invitation to correct the inferred basis, and a clean separation between provisional evidence and authority. That recurring gap warrants further testing, but the present evidence does not establish a distinct skill rather than a focused extension to existing review guidance. Do not author until independent trials show a broader standalone final-judgment gap beyond ordinary review and verification.

### Implementer

- **Trigger boundary:** An agreed contract or bounded work item needs an execution owner who will produce the scoped change and supporting verification. It should not trigger for planning, coordination, requirements authorship, independent review, or acceptance decisions.
- **Reusable invariant/workflow:** Clarify blocking ambiguity before changing work; translate criteria into the smallest coherent implementation; verify outcomes in proportion to risk; preserve unrelated work; surface assumptions, failures, and residual risks; and hand off the result and evidence without judging its own acceptance. Deliver the smallest coherent solution for the current outcome; do not silently add speculative capabilities, abstractions, or generalized infrastructure, and route a material scope expansion for decision. If formal requirements are absent, state the inferred scope and criteria, supporting evidence, and material uncertainty before relying on them, and never convert inference into authority. When execution reveals a required or clearly preferable established dependency, pause only the affected work, explain the need, and request installation, authorization, or contract clarification rather than silently installing, bypassing, or rebuilding it. Targeted documentation checks are appropriate; tool selection that changes the contract or introduces a meaningful dependency routes back to the controlling authority.
- **Must remain project-specific:** Technology stack, test strategy, commands, paths, allowed-file rules, branching and workspace conventions, evidence formats, deployment mechanics, approval gates, and team role arrangements.
- **Dependencies and overlap:** `coordinator` may provide scope or blocker routing and `contract-author` may provide formal requirements when those skills are present; neither is a runtime prerequisite. An implementer skill would own execution only, without absorbing orchestration, redefining requirements, or performing independent final review.
- **Evidence needed before authoring:** Develop independent cross-project cases showing failures that a role-scoped implementer skill prevents beyond existing coding, testing, planning, and workspace guidance. Use project role documents only for later comparison after that need and boundary are established independently.
- **Historical disposition:** Evidence-tested hold (2026-08-25; fresh task `01a03c1c-cbfb-7531-a2d4-71960d7ed7c8`). Across software, configuration, operational, and documentation controls, ordinary baseline behavior plus existing planning, TDD, workspace, coordination, and verification guidance already preserved scope and unrelated work, produced proportionate checks, surfaced risks, handed off evidence, and avoided self-acceptance. Three materially different no-contract controls did repeatedly convert reasonable inferences into settled execution criteria without labeling their evidence, provisional status, or uncertainty. That narrow provenance gap is portable, but it does not yet justify a broad standalone implementer role with substantial overlap. The hold called for further independent evidence of a compact execution-owner discipline beyond existing implementation skills.
- **Current disposition:** Astra evaluation completed 2026-09-16; standalone skill remains on hold. Nine fresh implementation trials compared baseline, narrow provenance guidance, and a compact candidate across software, configuration, and documentation; three additional boundary trials covered planning, independent review, and a trivial edit. No distinct material benefit over baseline or the narrow correction was demonstrated. The candidate is retained only under evaluation material, with no activation or existing-role correction. [Issue #1](https://github.com/philsaxton/codex-skills/issues/1), the [executed plan](docs/plans/2026-09-15-implementer-skill.md), and the [evidence/disposition](evals/implementer/2026-09-16/DISPOSITION.md) record settings, actual artifacts, checks, and limits. These small synthetic trials do not establish robustness, automatic host selection, or real dependency-adoption tradeoffs. Reopen when realistic failures demonstrate a portable gap; no permission or required-verification relaxation is proposed.

It also directs reviewers to reread truncated-looking evidence at its file path and report a genuine gap to the controller instead of regenerating the evidence with a suite rerun.
- **Observed duplication and a shipped correction:** [PR #2089](https://github.com/obra/superpowers/pull/2089), merged on 2026-08-06, reports duplicate reviewer suite execution on identical code in 5 of 8 control runs. Difficulty locating or reading prior evidence was the reported driver. The added rereading guidance produced no reviewer reruns in four treatment runs while reported outcome checks remained passing. These are upstream results from a small evaluation without a pinned model, not results reproduced here or evidence about the user's sessions. The fix is also recorded in the [v6.3.0 release notes](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/RELEASE-NOTES.md).
- **The exact wording conflict was raised:** [Issue #1961](https://github.com/obra/superpowers/issues/1961), opened on 2026-07-10, asks how reviewer evidence reuse reconciles with the fresh-execution rule. Maintainers asked for a real session example and closed it on 2026-08-19 when that request went unanswered. The closure does not establish that repeated reviewer execution is intentional.
- **Some separate checks are intentional:** [Finishing a Development Branch](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/finishing-a-development-branch/SKILL.md) requires a full suite before integration and tests on the merged result. Preserve applicable stage requirements and distinguish them from repeating an unchanged suite solely because another worker received the task.

Selective skill adoption could deliver the strict completion rule without the reviewer guidance that limits repetition. Test that integration hypothesis before retiring the skill; do not assume adding a new shared rule is necessary.

#### Lean debugging candidate

- **Trigger and outcome:** Investigate a reproducible defect, test failure, or unexplained behavior and establish an evidence-backed cause or an explicit limit on what is known. Repair only within the assignment's authority; a diagnosis-only request returns findings without product edits. Exclude routine implementation, acceptance review, and speculative audits.
- **Borrow:** Read the actual failure, reproduce it or collect missing observations, inspect relevant changes, trace inputs and state across component boundaries, compare working and failing cases, and test one causal hypothesis with the smallest useful experiment. Distinguish a product defect from environment or measurement failure. Preserve a regression check when useful and reassess attempts that no longer produce information.
- **Keep lean:** Scale investigation to the uncertainty. Avoid mandatory instrumentation at every boundary, fixed four-phase paperwork, a universal retry count, or the assumption that three failed fixes prove an architectural flaw. Permit explicitly identified mitigations within scope while retaining the unresolved cause. Return the observed failure, supporting and contrary evidence, cause or uncertainty, relevant repair/check results, and remaining limits.
- **Boundary:** Use testing practices where they help establish a regression; do not require another named skill. A verifier finding can prompt investigation, but the debugging worker does not take over the reviewer's verdict or change requirements to fit a repair.

#### Lean testing candidate

- **Trigger and outcome:** Create or improve meaningful development tests for changed behavior or a demonstrated regression. Focus on test design and the implementation feedback loop. Exclude tests for human prose or trivial changes without a meaningful behavioral risk, and do not turn final review into implementation.
- **Borrow:** Name the realistic break each test catches; derive expectations from requirements or independently checked examples; exercise observable behavior and side effects; and use focused failing tests before fixes or new behavior when a meaningful executable expectation is available. Confirm failure is for the intended reason, implement the smallest coherent change, and run affected checks owned by the assignment, preserving project requirements and handing off reusable evidence for broader review. Prefer adequate existing tests over duplicates. Keep essential behavior real when using test doubles.
- **Keep lean:** Avoid tests that mirror implementation, assert only source text, or exist solely to satisfy coverage or a test-per-function rule. Do not require deleting useful implementation because it predates a test. For tests added later, demonstrate detection using an isolated known failure or safe mutation where practical, and report any validation limit. Do not introduce blanket permission requests for routine exceptions; respect actual project requirements, including stricter test-first policies when present.
- **Boundary:** This skill supplies testing techniques; `verification-method-author` owns the broader lifecycle when the assignment is to create or maintain a reusable verification method. They may use the same test and evidence without duplicating files or requiring a chain of skill invocations. A passing development suite does not establish complete application conformance.

#### Shared completion rule candidate

Proposed wording to evaluate wherever workers make completion claims:

> Support completion claims with evidence applicable to the current state and assignment. Complete assigned checks and hand off their results, evidence, and remaining work. Reuse adequate evidence; rerun when relevant state changes, evidence is insufficient, or independent execution is required. Distinguish observed results, reused evidence, failures, and unverified behavior. Overall completion requires every required check to be satisfied; a handoff alone requires no rerun.

- **Coverage and placement:** The rule must reach implementers and single-context work, including non-application deliverables that `verifier` excludes. Keep one canonical portable rule in this repository's shared workflow guidance; choose and test its delivery mechanism during evaluation. Consuming projects select how it reaches every worker through their controlling instructions or handoffs. Loading `coordinator` or `verifier` in some tasks is not sufficient coverage. Keep project commands, evidence locations, stricter freshness requirements, and approval gates local.
- **Evidence meaning:** Reuse earlier evidence only when its identified artifact or application state, method, inputs, dependencies, and environment still support the claim, and label that reuse. Rerun affected checks when they change or applicability is uncertain. Avoid reruns merely because a message or role changed. Preserve adverse results and required checks; a narrow passing check cannot stand in for an unrun build or failing suite.
- **Retirement dependency:** Superpowers `systematic-debugging` explicitly invokes both `test-driven-development` and `verification-before-completion`. Inventory these and other direct paths, selected links, prompts, and handoffs before switching. Removing discovery links alone does not retire those instructions. Evaluate explicit replacement routing without editing the pinned vendor; if the reference cannot be resolved cleanly, retain the affected old workflow pending a supported transition.

#### Scoped handoffs and verification ownership

- **Complete the assignment:** Define each worker's output and assigned checks before work starts. An implementer may finish its scoped change and development checks while application review remains assigned to the reviewer. Report that state as ready for review, with remaining work named. A blocked or incomplete assignment may return findings for routing, but must not claim completion. Do not require every worker to finish the whole workflow before handing off.
- **Give shared checks one owner:** Assign each required full suite or other shared check to an existing worker, reviewer, or CI job; do not create a new role. Reuse its applicable result across handoffs and coordinate around an existing run instead of starting duplicate runs for the same state. The coordinator, or the responsible worker in a single-context task, ensures that every required check has an owner and a result before overall completion. Project rules still determine any required stage or independent execution.
- **Keep review independent:** The reviewer independently examines requirements, changes, assertions, coverage, and actual evidence, and owns the judgment about whether they establish the requested behavior. A previous agent's success summary alone is insufficient. Adequate execution evidence can support that judgment without repeating execution. Run or route checks for uncovered behavior, suspect results, or changed state; use a full rerun when project policy or the affected scope warrants it. Independence of judgment and independent execution are separate requirements.
- **Pass a usable receipt:** Reuse the project's existing report or a small handoff containing the checked state, including relevant uncommitted changes; commands or actions; method, inputs, dependencies, and environment; output locations and results, including failures; coverage limits; and remaining checks with their owners. If the evidence is inaccessible, mismatched, or insufficient, resolve the gap or rerun the necessary checks. Record the reason for additional execution. This is a small addition to existing handoffs, not a new registry or harness.

### Running discrete shell commands

- **Trigger boundary:** Command-line work is about to combine independently meaningful operations or obscure them behind shell convenience constructs. It should not burden a single direct command or a short readable pipeline whose stages form one data flow.
- **Reusable invariant/workflow:** Put one small coherent operation in each command tool call; run independently meaningful sequential operations as separate calls; allow short readable pipelines; prefer literal arguments and explicit paths; and do not hide operations in variables, substitutions, heredocs, generated scripts, or functions merely for convenience. Necessary shell complexity uses the smallest transparent form and is explained.
- **Must remain project-specific:** Sandbox permissions, approval configuration, command authorization, repository commands and paths, shell and tool interfaces, writable locations, and temporary-file policy. The skill changes none of those controls.
- **Dependencies and overlap:** The approved [design specification](docs/superpowers/specs/2026-08-25-running-discrete-shell-commands-design.md) defines the boundary, and the [implementation plan](docs/superpowers/plans/2026-08-25-running-discrete-shell-commands.md) defines the evaluation and delivery. The skill shapes command form only, without replacing authorization, safety, or workspace guidance and without requiring another named skill.
- **Evidence needed before authoring:** Execute the planned fresh-context controls and skill-guided pressure scenarios for chained Git operations, readable pipelines, and shell indirection; verify that the guidance separates independent work without producing awkward workarounds or broadening authority.
- **Current disposition:** Implemented and independently verified (2026-08-26). Fresh neutral baselines showed mixed behavior without the target skill: some agents kept operations separate, while others chained independently meaningful inspection, staging, verification, and commit work; a readable pipeline remained one data flow, and an indirection control used direct calls. The [running-discrete-shell-commands skill](running-discrete-shell-commands/SKILL.md) applies the smallest portable command-shape rule without changing authorization or project policy. ## Project-policy boundary

The following are control-plane choices, not standalone reusable skills: exact retry counts, project status names, evidence paths, record schemas, backlog selection rules, and repository permissions. They may configure a reusable workflow but must remain in the applicable project's authoritative instructions.

Likewise, worktree creation, commit construction, merge strategy, and push mechanics overlap with dedicated Git/worktree workflows. Extend those workflows only for a demonstrated reusable gap; do not recreate them inside coordination, change-control, or review-loop skills.

Revisit this backlog when new project evidence changes a candidate's boundary, demonstrates a missing invariant, or shows that an existing skill already covers the need.
