# Build the garage around existing work

Read this when workspace setup requires separating existing content. Use the entry point's domain ownership rules; this reference supplies the migration procedure, not a second skill or an automatic cleanup mandate.

## Map the existing connections

Inventory the affected repositories and their tracked, untracked, ignored, staged, and dirty content. Include hidden control files and symlink targets. Establish which repository owns each path; a directory containing a `.git` file may be a linked worktree or submodule rather than a movable standalone repository.

Distinguish a garage containing independent repositories from an application repository containing several components. Keep a shared-history suite together unless repository extraction was separately requested; directory names do not establish independent applications or origins.

Trace producers and consumers of paths being changed: application settings, scripts, tests, scheduled jobs, shared reports, local adapters, and instructions. Separate intentional product assets from runtime outputs. Preserve supported interfaces and human-facing application docs with the application.

Include existing scratch locations, active writers and registered application worktrees in that map. For each worktree, record its owning Git repository, branch or detached commit, tracked/untracked/ignored changes, and any host task association. Add garage-local scratch/worktree defaults for future use without sweeping old directories into cleanup. Keep contracts and recovery copies outside disposable scratch. Worktree placement changes require Git-aware relocation and shared-metadata access, not an ordinary directory move or a scratch cleanup command.

When proposing the layout, offer a direct child application directory for a workspace with one application, such as `workspace/application/` alongside `docs/`, `artifacts/`, `.recovery/`, and workspace support under `.agents/`. Default vendored skills to `.agents/vendors/<dependency>/` and selected activation links to `.agents/skills/`. An `apps/` container adds a directory level without separating additional applications in that case. Offer `workspace/apps/<application>/` when grouping multiple independent applications would help, or when the user prefers that convention. Preserve an established layout unless changing it serves the requested refactoring; do not relocate an already organized single application merely to remove `apps/`. Record the selected layout and exclude the actual application directory (for example `/application/` or `/apps/`) from the outer Git index. The scaffold's `apps/` layout is an option, not a requirement for migrations.

Produce a compact migration map with source, destination, owner/repository, affected references, and verification. Record uncertain ownership explicitly. Resolve only material ambiguities that prevent a safe migration; use established conventions for routine choices.

Use that inventory to show the user a proposed directory tree or diagram and the associated keep/copy/rename decisions, including independent Git roots and documentation, artifact, recovery and scratch locations. Discuss names and project-specific layout needs before creating the garage or changing existing files/indexes. Let the user revise the proposal and approve the resulting migration plan; reuse an already approved specific plan rather than asking again. Record the agreed structure in the contract. The default scaffold is one possible implementation, not a mandatory shape for every workspace; material layout changes return to planning, while routine execution of the approved map continues.

Classify existing `AGENTS.md` content by purpose, not as a whole document. Preserve product build/use requirements and contributor conventions in the application's human-facing docs; transfer local Codex-agent governance and support guidance to the garage. Reconcile with existing docs, preserve requirements and their meaning, and update links before removing authorized old copies. Record unresolved conflicts rather than silently dropping requirements. Relocating a checkout intact preserves history but does not complete this separation. Keep product-supported interfaces and their documentation with the application.

## Authorize the governance transition once

For an existing project whose rules govern changes to instructions or document authority, inspect those rules before moving directives or changing their scope. Prepare one coordinated migration amendment through the existing amendment process, using the inspected migration map. This applies to refactoring a governed project, not ordinary new-workspace setup; do not invent an amendment process where none exists.

The amendment should cover:

- **Permitted refactoring:** Identify affected documents and directives, their destinations and ownership, permitted moves/removals/edits, and required updates to references. Include agent-directive extraction and destination cleanup, not just the original checkout's retirement notice.
- **Future authority:** Specify which application requirements remain under the application's governing workflow and which operational directives become workspace-owned under an explicitly defined lighter maintenance process. Physical separation makes that boundary discoverable to humans and agents. A change affecting application requirements, approval authority, or release obligations remains application-governed even when written in a workspace file; routine workspace preferences need not inherit the application's full amendment process.
- **Transition controls:** Define when the migration begins, who can approve urgent exceptions, where authorized changes occur, and the development pause described below. Keep the original identified as undergoing migration until verified cutover, with retirement effective according to the approved disposition.
- **Acceptance and recovery:** Define preservation and verification checks, any required implementation review, cutover authority, rollback or recovery conditions, and retention/deletion or notice scope for the original. State when temporary migration authority ends and the destination's separate processes take effect.

Obtain the required approval before executing governed changes. Copying documents into a new checkout does not release them from their existing rules. After approval, perform covered migration steps under that amendment without reopening the complete amendment workflow for every edit. Preserve any review checkpoints it requires. Material scope changes return to the controlling approval process; unrelated application work retains its normal rules. This is bounded migration authorization, not a general suspension of governance.

### Pause development; handle continued use separately

From the agreed migration start until verified cutover, pause ordinary development across the affected checkouts, worktrees, and agent tasks. Allow migration work and explicitly approved urgent fixes only. Coordinate that pause with active writers; a notice alone does not stop them. Record each urgent exception, preserve its changes, and reconcile it into the destination before cutover. If migration is abandoned, explicitly restore the original development authority rather than leave the pause unresolved.

Continued application use is a separate decision and may remain available. If usage changes data or outputs being migrated, define how those writes will be captured and reconciled, or arrange a bounded pause for the relevant transfer. Do not assume either that a development pause stops operational writes or that migration requires shutting down an otherwise usable application.

## Save the migration contract

Record the authorized outcome, source/destination and ownership map, instruction-requirement destinations, preservation evidence, ordered migration steps, acceptance checks, recovery route, and unresolved decisions. For a governed migration, reference the approved amendment and its scope, checkpoints, development pause, exceptions, and future authority boundary; the contract may serve as that amendment when the existing process permits, without a duplicate approval document. Include the stable session context and access needed for relocation. When available and useful, `contract-author` may help draft this record; otherwise write the same concise record directly.

This is lasting workspace documentation: default its authoritative home to tracked `docs/workspace-migration.md`, alongside workspace plans and decisions. Verify that path is eligible under the garage's selected tracking policy, separately from retained application reports in `artifacts/`; the default explicit-directory exclusions need no per-document exceptions. Application-specific documentation stays application-owned. Default raw backups, preservation manifests and recovery evidence to ignored `.recovery/workspace-migration/`, separate from `artifacts/` and scratch. Use access-appropriate storage for machine-local or sensitive evidence; the contract should reference needed evidence without indiscriminately embedding or tracking it.

Save it durably in a non-scratch location accessible to the current session before copying the application. If the garage is not writable yet, identify that interim authoritative location and its intended destination in tracked garage docs; do not make it application-owned merely because the current session starts there. Keep the original workspace available while the agent finishes the contract and supporting handoff documents; transfer the latest record once destination access is established, obtaining any missing environment approval.

Maintain exactly one authoritative migration document at each stage. Verify the delivered revision/content before recording the authority transition in the source record, destination record and handoff. Link the current authority from garage instructions or README. Mark retained handoff/recovery copies as snapshots, with their source revision/content identity and a pointer to the current authoritative location; they are not parallel editable contracts. Keep snapshots out of disposable scratch, and update their forwarding information when authority moves. Record completed/pending steps and post-copy changes in the authoritative document. The receiving session must follow the authority pointer and reconcile current state before continuing, not select a copy by modification time or resume from a stale snapshot. Conversation memory alone is not the migration contract. Keep a concise current-status summary at the top: authoritative development path, verification still needed, retained dependencies, and remaining user decisions. Date detailed receipts below it and mark superseded decisions; do not leave readers to reconstruct current status from an accumulating chronology.

Include an explicit cleanup recommendation for the retained original checkout: its exact path outside the new garage, verification and reconciliation still required, any remaining writers or sessions using it, retained recovery material, and the approval/access needed to remove it. Mark this cleanup pending until it is performed or the user elects to retain the original; copying the app does not itself authorize deleting the old checkout.

## Enclose an existing application repository

When launched at the application's Git root, establish a dedicated enclosing workspace and place the intact application repository beneath it. Before creating or copying paths, ask for the new workspace name/location and any desired application-directory renaming unless the user already supplied those choices. Do not automatically append “garage” to the app's name. Preserve names that the user has not asked to change, distinguish folder renaming from repository/product identity changes, and record the agreed path mapping and affected references. Do not silently make a shared parent such as `Projects/` the garage, reinitialize the application, or turn its current index into a governance-only index.

1. Record the exact source and destination, repository type, history/branch/origin, index state, and working data to preserve. Keep a shared-history suite as one repository. A linked worktree or submodule needs a Git-aware transfer preserving its relationships; copying its directory alone may leave metadata pointing to the original and is not sufficient.
2. Prepare the layout and contract locally, complete any required migration-amendment approval, and activate the agreed development pause. Establish actual access before writing the new garage. Setup authorization covers the empty-garage scaffold for the chosen container but does not waive environment approval. Do not run it against the occupied checkout or enable a force mode.
3. Default to copying an ordinary application checkout intact into the garage, retaining the original so the active agent can continue writing and delivering handoff documents. Preserve `.git`, staged changes, untracked/ignored data and required file relationships; a fresh clone alone omits local work. Coordinate writers to obtain a consistent copy and verify preservation before separating domains in the destination. Stop only the dependent step if destination, preservation or access is unresolved. Use a direct move only when explicitly chosen from a stable session outside the source that will remain valid afterward.
4. Track changes after the copy, including newly written handoff documents, index changes and runtime output. Before switching the authoritative application to the destination, reconcile those changes without overwriting destination work, deliver the latest handoff documents and record the cutover. Do not let both copies continue as independent writable authorities. Keep the original available for recovery and cleanup, not as an unnoticed second active application.
5. Open the garage as the intended agent workspace; verify its instructions, selected skills, effective permissions, application identity/local work and any remaining dependencies on the old checkout. A shell `cd` or skill script does not change the sandbox or loaded instructions. Continue domain separation there and report operational handoff separately from pending old-checkout cleanup.

## Reconcile worktrees and task associations

Copying the main checkout does not transfer external worktrees. In an independent destination copy, do not retain copied registrations that still point at worktrees owned by the original Git metadata. Keep the originals valid while deciding where their work belongs.

Handle each worktree according to its actual state:

- **Completed and merged:** No replacement is needed. When cleanup is authorized, verify it is unused, clean including ignored content, unlocked, and merged into the intended destination before removing it through Git.
- **Unfinished work:** Preserve its base commit, staged and unstaged distinctions, and untracked or ignored files. Transfer into a destination-owned application worktree when authorized, verify the transfer, and name the copy where development will continue. A retained backup is not integration, and copying files does not move a host task's working directory or permissions.
- **Uncertain or divergent:** Keep the work isolated and identify the specific decision needed. Do not force a merge or deletion merely to finish setup.

For a task that will continue from an old worktree, use supported host controls for relocation or continuation. If unavailable, report the association as a remaining dependency and provide the destination path. If the user elects to discontinue the old task, record that disposition instead of requiring its relocation. Do not claim task migration from a file copy alone. Apply authorized cleanup after rechecking dependencies, without expanding setup into unrelated branch cleanup.

## Choose and apply a reversible migration

- A nested application repository already excluded from the garage can stay where it is. Avoid moving paths merely to fit a preferred spelling or layout.
- Capture the relevant starting state and a recovery route before mutation. Preserve unrelated dirty/staged work; do not reset it, stash it implicitly, or include it in migration commits. Check destination collisions before copying or moving. For active outputs, coordinate producers so that writes are not lost during the transition.
- When migration paths have staged changes, compare HEAD, index, and working-tree content; preserving the visible file alone can lose a distinct staged version. Preserve or resolve those versions before changing the index. A failed untracking command is not permission to force it.
- On a retry or interrupted migration, reconcile the actual source, destination, and current consumers against the migration map before resuming. Identical copies and divergent copies need different decisions. Never choose a canonical report by modification time alone or overwrite an existing destination to make the layout match.
- Apply only authorized moves and configuration changes. Copy valuable runtime data first when that allows verification before removing the old copy. Update producers and consumers together and preserve application-supported standalone defaults. Use local orchestration for garage-specific paths rather than hard-coding them into the product.
- Handle tracked files explicitly. Changing `.gitignore` does not remove them from an index. Where removing a generated file from tracking is authorized, keep the working data and change only the intended index entries. Do not rewrite history to tidy old artifacts. Intentional fixtures or published deliverables may need to remain tracked.
- Treat linked worktrees, submodules, and symlinks according to their actual relationships. Do not blindly move `.git` metadata or retarget a protected instruction/tool installation as part of cosmetic organization.
- Inspect application-local leftovers after support transfer, including ignored runtime directories and old installation containers. Within the approved separation scope, remove empty obsolete directories or preserve and relocate their contents according to ownership. Do not classify reusable installation helpers or intentional fixtures as workspace metadata merely because their names resemble local tooling; update callers and validation when moving a supported helper.

When migration changes what trusted tooling executes or who can edit it, check the affected script, imports/dependencies, symlink targets, and configuration against its actual execution permissions. Ordinary sandbox execution remains sandboxed; a standing approval for an outside-sandbox command does not pin the script's contents or dependencies. If the move makes higher-permission execution depend on newly editable code or configuration, record and resolve that specific trust change before activating it. This focused migration check is not a general vulnerability audit and requires no separate review skill.

An inspection or planning request stops at the migration map. Authorization to implement a defined migration carries through its routine reversible steps; do not repeatedly ask permission for work already approved. Stop only the dependent action if preservation, ownership, destination, or permission remains unresolved.

## Verify before retiring old paths

Check preserved data using content comparisons or hashes as appropriate. Run the affected producer-to-consumer workflow using the new locations, and search for stale references in the affected scope. Compare application roots, histories, and origins; inspect each repository's index and unrelated dirty state. Verify a standalone checkout when application behavior changed.

Keep old data or recovery material until the replacement is verified; remove it only when authorized. Report three outcomes separately:

- **Preservation:** What was copied and verified, including differences that still need reconciliation.
- **Operational cutover:** Whether the destination has the required instructions, access, application behavior, and an agreed development authority. List any old tasks or consumers that still need transition.
- **Original disposition:** Removed, intentionally retained, or awaiting a concrete decision/dependency. Intentional retention need not block operational cutover, but an unresolved required consumer does.

State verification evidence and remaining actions for each outcome. Repeat checks when files, consumers, or execution context changed; carry forward earlier applicable evidence explicitly rather than rerunning unrelated suites. Return the final domain map through the entry point's completion receipt.

For copy-first handoffs, recommend cleanup of the exact original app path once the receiving workspace works, post-copy differences are reconciled, necessary recovery material is retained, and no agent, writer, worktree or consumer still depends on it. Recheck those conditions immediately before removal and use existing explicit cleanup approval or obtain it if missing. An original checkout outside the new workspace may also need separate filesystem permission. Never route it through the scratch remover or delete it merely because a destination with the same name exists. Record removal, intentional retention, or the remaining cleanup action in the handoff receipt.

## At cutover: confirm the original checkout's disposition

After the receiving garage is verified and post-copy differences are reconciled, record the new application authority, the end of the development pause, and the separate application/workspace processes taking effect. Execute the original disposition already approved in the migration amendment or contract. If disposition remains unresolved, confirm whether the original will be deleted or retained; seek further amendment approval only when the existing rules require it for an uncovered change. If immediate deletion is authorized and its preservation, dependency and access checks pass, remove the old copy without first adding a redundant retirement notice. Follow any project rules that apply to deletion itself; skipping a notice does not waive those rules.

Retirement is an optional safeguard for a retained original, not a mandatory migration workflow. When retention is chosen and the old copy could be mistaken for active work, confirm the need for a notice and include its scope in the migration contract. During the transition, record which copy may receive development changes and coordinate existing sessions and writers; a later retirement notice does not prevent divergence before cutover.

If a retirement notice is needed, use its already approved scope and complete the migration amendment's required review checkpoints. If it was not covered, follow the original project's amendment rules before changing governed documents. Do not repeat completed approval stages merely because this is the final migration step, invent a mandatory role sequence, or use a different marker file to bypass governing requirements.

Apply the approved notice to the original checkout only: identify it as retired from development, point to the new garage/application and authoritative migration document, and explain its retained recovery purpose. Ensure the notice is discoverable through the project's approved entry point, verify its links and scope, and confirm the new application has not inherited an obsolete retirement notice. Coordinate any still-running sessions explicitly; editing a file does not establish that those sessions have reloaded it.

Record the chosen disposition in the authoritative migration document: deleted, retained with retirement completed or pending, or retirement not needed with the reason. If a required governing review, permission or session transition is unresolved, retain the original and report that specific pending step rather than claiming retirement is enforced. Keep a retained recovery copy until its retention conditions and explicit deletion approval are satisfied.
