# Set up a project in cloud

Use this mode when recovering a selected project checkpoint or checking whether a cloud workspace has the prerequisites for development. Keep the existing garage's organization and application governance. This is a setup boundary, not ongoing backup, publication, deployment, or project-acceptance orchestration.

## Establish the setup target

1. Read the selected garage's `AGENTS.md`, the application's contributor/startup instructions, and required project skills. Establish the approved repository, work ref, exact commit and root tree. Preserve surviving files; recover into a fresh location when restoration is authorized. Do not substitute current main for draft-branch work.
2. Locate the versioned `workspace-setup.json` beside that garage's `AGENTS.md`. Keep it with portable garage support and include it in an authorized garage export. Check its identities against trusted source evidence. If absent, prepare a project-specific profile from inspected requirements; the examples below are synthetic, not approvals or current project configuration.
3. Establish source acquisition separately. Prefer the supported GitHub connector. The recovery dependency expects complete Git-data commit metadata, non-recursive trees, base64 blobs and selected ref observations in its documented connector bundle. Check the actual connector response before choosing a route: raw/base64 response limits and large blobs may make this unavailable. No connector-to-shell bridge is implemented here. Report the missing exact bytes; use another exact-byte route only when supported and authorized. Never reconstruct bytes from excerpts or invent Git history.
4. Use the existing reviewed recovery tool only for separately authorized acquisition/materialization steps. Then run the read-only check below against the actual local workspace. It does not restore a garage, fetch content, install tools, register skills, execute profile commands, or mutate a provider.

## Dependency and invocation

Python 3.9+ and a POSIX filesystem are required. Genuine-history checks also require a system Git installation. All other checks work on source snapshots without `.git`.

The recovery implementation is bundled under `scripts/recovery/`, with the reviewed release's source-tree expansion correction. [recovery-dependency.json](recovery-dependency.json) pins both modules; [provenance and test routing](recovery-provenance.md) records the original release, deliberate revisions and tests. The default resolves relative to this skill, independent of its installation path or the working directory. Missing or changed bytes stop validation. Both modules are hashed before either is loaded; ambient modules and cached bytecode are not used or written. An optional `--dependency-dir /absolute/path/to/release` selects an alternate local copy with the same mandatory pins. No downloader or dependency installation occurs.

```sh
python3 <skill-directory>/scripts/check_cloud_readiness.py \
  --workspace /absolute/path/to/garage \
  --context current-session \
  --host-observations /absolute/path/to/private/host-observations.json
```

The explicit workspace must be a real, absolute directory. All profile paths, including source bundles, controls, recipe files, report parents, private manifest/hash companion and selected private inputs, resolve from that workspace, never the shell's current directory. Skill resource paths resolve conceptually from the registered skill's root and are compared with the host observations; they are not paths to arbitrary local installations. The helper rejects traversal, symlink components, special files and hard-linked inspected files. Source symlinks and linked-worktree Git metadata are unsupported in v1 and report unavailable; do not relocate working files to make the check pass.

The helper writes only JSON to stdout. Retain output in an appropriate private evidence location when needed. Exit codes: `0` means development and all nonoptional groups' listed prerequisites are ready; `1` means at least one is blocked or unverified; `2` means the profile/dependency could not be validated. CLI syntax errors use normal argparse usage output. Optional groups still report their own failures. None of these outcomes says tests passed or the project was accepted.

## Profile and evidence formats

[cloud-readiness.schema.json](cloud-readiness.schema.json) is the versioned, closed JSON Schema. The root validates profiles; `#/$defs/host` validates host observations and `#/$defs/privateManifest` validates the private input manifest. The dependency's connector-bundle format remains authoritative for source evidence. Unsupported fields and duplicate JSON keys are rejected.

The source bundle is JSON with `version: 1`, `provider: "github_connector"`, `snapshots` and `references`. Each snapshot contains `repository`, `requested_commit`, `retrieved_at`, the connector's `commit` metadata (matching `sha` and `tree.sha`), all reachable non-recursive `trees`, and all reachable `blobs`. Trees contain `sha`, `truncated: false` and entries with basename `path`, Git `mode`, `type`, and child `sha`; blobs contain `sha`, `encoding: "base64"`, complete `content`, and byte `size`. Each reference contains `repository`, exact `ref`, `observed_commit`, and `observed_at`. The bundled `garage_workspace.py` functions `validate_bundle` and `validate_source_objects` define accepted optional Git-data metadata fields. No excerpts, recursive/truncated trees, LFS pointers, submodules, unused or missing objects satisfy that format. The bundled recovery tests construct complete connector-shaped examples without contacting a provider.

- `governance`: workspace-relative paths and SHA-256s, including the root `AGENTS.md`. Hash matching proves the selected bytes, not that the runtime loaded them; verify effective instruction loading with the current host.
- `applications`: stable ID, local path, repository, selected work ref, exact SHA-1 commit/tree and source-bundle path/SHA-256. Applications must not overlap. All applications sharing one bundle must select its exact repository/commit/ref inventories. The dependency verifies every Git blob and tree, and the helper compares the complete selected tree's local files. Extra unselected files, private data, outputs and `.git` are not scanned by the source check. This is a selected-source-byte check, not a clean-worktree attestation. Supplied connector metadata binds commit to tree; the helper does not authenticate the provider. An observed moved ref is reported without changing the selected checkpoint.
- `skills`: registered names in `id`, SHA-256 of `SKILL.md`, and required resource paths/hashes, including that same `SKILL.md`. `tools` declares exact required observed version strings, not version ranges.
- `recipes`: local documentation path/hash and reviewable command strings. These are data only, never executed, expanded or imported. Project setup and test execution continue through ordinary authorized tools after review.
- `development`: shared requirements for all groups. `groups` name independently checkable test/report prerequisites, select a recipe and mark whether the group is optional. Each requirement set selects skill/tool/input IDs, explicit Git prerequisites, fixture/control `files`, and `report_parents`. Only declare a shared requirement when every group really needs it. A missing private audit input should not block a build that does not consume it.
- `inputs`: public-safe input IDs only. `private_manifest` is either null or the selected local manifest path, SHA-256 and `sha256_file` companion path. Keep private links, file inventories and sensitive provenance in the private package, not the publishable profile. This v1 manifest adapter contains `version`, matching `profile_id` and entries with `id`, relative `path`, `sha256` and byte `size`; it is deliberately smaller than the recovery tool's whole-export manifest. Its hash companion contains the 64-character digest with an optional newline. Select only needed input entries from a verified private source; no download happens. Unselected file contents are never read. Known credential paths/content are refused; sanitization still needs human judgment.

Additional helper rules enforce cross-references, unique IDs/resource paths, exact hash spelling, valid refs and matching identities. JSON inputs are at most 1 MiB, arrays at most 128 items, and one profile at most 1,024 emitted checks. Source bundles retain the dependency's 128 MiB bundle / 32 MiB blob limits and permit at most 10,000 expanded entries in total across all selected checkpoints. Each directory, file and symlink path occurrence counts, including repeated paths in different checkpoints and every occurrence of a shared subtree; the implicit root does not count. Traversal refuses the next entry before allocating its expanded path or inventory entry. Standalone source-object validation uses the same 10,000-entry maximum. This budget can reject otherwise valid large source selections; do not bypass it by silently changing the selected checkpoint or acquisition scope. Selected private files use the existing 2 GiB streaming limit. Quiesce writers while checking: ordinary concurrent mutations are detected, but this is not an atomic snapshot against hostile concurrent processes.

## Supply host observations honestly

Use the current runtime's supported inventory/registration mechanism to establish registered names and identities, then read each required resource. Disk files or activation symlinks alone do not prove registration. Do not manufacture a positive observation when the host cannot expose that state. Missing host evidence blocks the affected prerequisites while source checks can still succeed. Tool availability/version observations likewise come from an actual supported host check, not a profile assertion.

Host JSON contains `version: 1`, the exact raw profile file's `profile_sha256`, canonical absolute `workspace`, caller-selected `context`, UTC `observed_at` and `expires_at`, and `skills`/`tools` arrays. Skill observations contain `id`, `registered`, `sha256` and resources with `path`, `sha256`, `readable`. Tool observations contain `id`, exact `version`, `available`. Bind `context` to the current session/runtime, use that same value on the command line, and refresh after context changes. Timestamps accept `Z` or `+00:00`; the maximum validity window is one hour. Future, expired, malformed or wrong-profile/workspace/context evidence cannot establish readiness.

Successful host checks are explicitly `observed`, not independently authenticated. The overall `host_trust` field preserves that boundary even when a section is ready. The helper cannot prove an observation author used the real host or that a runtime remained unchanged afterward.

## Check expensive groups before running them

For genuine Git requirements, the helper uses fixed read-only commands to compare HEAD and the selected commit's actual tree, verify named commit objects, and, when requested, inspect reachable history for missing objects. It does not fetch, repair or create history. Partial/promisor storage, alternates, executable/include or unsupported Git configuration, unsafe metadata and linked worktrees report unavailable. Full-history requests reject shallow repositories. Ambient Git configuration, replacement objects, hooks, credential helpers and lazy-fetch transport are disabled. A source snapshot can be source-ready while a history-dependent group is blocked.

For reports, check exact required Git identity and fixture/control hashes as group prerequisites. The report parent must exist and be a real directory. The helper makes no write probe: even a positive access observation leaves report writing `unverified`, with section status `unverified` unless another failure blocks it. Establish actual report-writing ability through a separately authorized smoke test before expensive work. V1 does not consume smoke-test or prior-test receipts; record that external evidence separately rather than relabeling this helper's uncertainty.

Report `source`, `development` and each named group separately. `ready` means only the declared checks succeeded within their reported trust boundary. `missing`, `malformed`, `mismatch`, `stale`, `unsafe` and `unavailable` checks block their consumers; `unverified` never becomes ready. Results always retain `tests: not_run` and `acceptance: not_assessed`. Apply the project's own review/test/acceptance gates afterward.

## Sanitized examples and handoff

- [Scope-like](cloud-examples/scope-like.json): selected source bytes and fresh supplied skill/tool evidence can satisfy ordinary build prerequisites without Git history
- [ACKS-like](cloud-examples/acks-like.json): a selected private extract and hash companion gate an optional audit; their absence leaves the unrelated build ready
- [CAW-like](cloud-examples/caw-like.json): report prerequisites additionally need real HEAD/historical objects, a control file and a report parent; a source snapshot cannot satisfy those history checks

These profiles use fictional repositories, commits, versions and synthetic-byte hashes. The tests construct the corresponding isolated fixtures and exercise all three. Replace every identity with inspected evidence before actual use.

Hand back the selected profile/hash, governing source evidence, source/development/group results, verified recovery checkpoint and explicit remaining acquisition, history, registration, private-input or report-write gaps. Keep private evidence references in the private handoff. No complete recovery, effective runtime registration, passing tests, automatic backup or ongoing checkpoint service follows from this setup receipt.
